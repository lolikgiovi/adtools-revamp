# Production timestamp repair, 30 October 2026

Applied `backend-workers/scripts/repair-analytics-timestamps-2026-10-30.sql` to
production D1 `adtools` after user authorization. It repairs the 29 October
redeployment regression in client-ledger IDs 34642 through 34758.

## Result

- Exactly 64 timestamps corrected by seven hours, each supported by the separate
  event stream for the same device and tool at the corrected second, with no event
  evidence at the original wall time.
- 37 rows moved from 30 October back to 29 October.
- The reported 03:04:04 activity (ID 34758) now reads `2026-10-29 20:04:04+07:00`.
- All 3,365 records from the prior repair remain correct.
- Compared every field of all 253 recent backed-up rows against the expected
  result: only the 64 selected timestamps changed. This includes 144 later rows
  outside the regression range, which remained intact.
- Total ledger rows increased from 34,310 to 34,311 through concurrent ingestion;
  the repair did not insert or delete usage rows.

Original timestamps, corrected timestamps, stable event IDs, and evidence IDs are
retained in `analytics_timestamp_repair_20261030`. Private backups and verification
outputs are in Git-ignored `.wrangler/backups/analytics-timestamps-repair-20261030/`.

## Validation

Before applying the repair, exported the entire `tool_usage` table and captured 436
relevant event-evidence rows. A local SQLite rehearsal against all 34,310 backed-up
rows verified exactly 64 changes, preserved all other fields, and confirmed a rerun
made no further changes. Before the production mutation, the entire target ID range
was compared again with the backup and matched exactly.

The regression test was written before the new repair SQL. It covers range bounds,
already-correct times, unsupported/ambiguous evidence, historical rows, wrong tools,
midnight crossing, repeat execution, non-time fields, and reversible rollback.
Both repair tests pass:

```bash
./node_modules/.bin/vitest run backend-workers/tests/analytics-timestamp-regression-repair.test.js \
  backend-workers/tests/analytics-timestamp-repair.test.js
```

Repeatable read-only production verification (expected: 64/64, 37 date changes):

```bash
./node_modules/.bin/wrangler d1 execute adtools --remote --env '' --command \
  "SELECT COUNT(*) AS audited, SUM(t.created_time=r.corrected_time) AS verified, SUM(substr(r.original_time,1,10)!=substr(r.corrected_time,1,10)) AS date_changes FROM analytics_timestamp_repair_20261030 r JOIN tool_usage t ON t.id=r.tool_usage_id AND t.event_id=r.event_id;"
```

Guarded rollback, if needed after review:

```sql
UPDATE tool_usage
SET created_time = (
  SELECT r.original_time FROM analytics_timestamp_repair_20261030 r
  WHERE r.tool_usage_id = tool_usage.id AND r.event_id = tool_usage.event_id
)
WHERE EXISTS (
  SELECT 1 FROM analytics_timestamp_repair_20261030 r
  WHERE r.tool_usage_id = tool_usage.id AND r.event_id = tool_usage.event_id
    AND r.corrected_time = tool_usage.created_time
);
```

This repair targets the confirmed later regression. It does not infer timestamps
for uncorroborated older records excluded from the first repair.
