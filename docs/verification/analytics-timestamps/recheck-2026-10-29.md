# Activity timestamp regression after redeployment

Read-only production checks at approximately 20:20–20:22 Jakarta on 29 October 2026
confirmed the reported Activity log at 3 AM was stored seven hours ahead.

## Evidence

- Latest usage row 34758: `2026-10-30 03:04:04+07:00`, JSON Tools `copy_output`.
  Two independent event rows for the same device/tool have wall time
  `2026-10-29 20:04:04`; none match the stored usage wall time.
- Of 109 client-ledger rows after ID 34641, 64 match event evidence seven hours
  earlier, and 45 match event evidence at their stored wall time.
- All 64 shifted rows were more than five minutes in the future when checked;
  37 had crossed into 30 October. These counts describe that snapshot.
- All 3,365 previously repaired rows still match the repair audit table.

Deployment history shows the fixed version `14d43769-a6a1-417e-bd5b-5d41eb17b434`
became active at 10:43:58 Jakarta. A later deployment activated
`330c58e9-2261-4757-8ef4-7b559a136940` at 14:09:32 Jakarta.
Reading the currently deployed Worker bundle confirmed that `tsToGmt7Plain` again
uses `Date.parse(String(s || ""))`, followed by adding seven hours. It lacks the
explicit Jakarta offset handling present in the local working tree. This explains
why new rows became shifted again despite the earlier repair remaining intact.

The local regression test passes:

```bash
TZ=UTC ./node_modules/.bin/vitest run backend-workers/tests/analytics-timestamps.test.js
```

It exercises client serialization, real ingestion, retries, and the authenticated
Activity report. One test passed. This verifies the local fix, not the running Worker.

## Reproduce the production audit

```bash
./node_modules/.bin/wrangler d1 execute adtools --remote --env '' --json \
  --command="$(cat backend-workers/scripts/audit-analytics-timestamps.sql)"
./node_modules/.bin/wrangler deployments list --env '' --json
```

The SQL contains only SELECT statements and emits no user emails or device IDs.
Event matches corroborate a timestamp shift; they do not independently establish
one-to-one action identity or count accuracy.

No production deployment or database mutation was performed during this recheck.
Resolution requires restoring the fixed parser in the active Worker and separately
repairing the newly affected rows with an audited, evidence-based repair. The first
repair deliberately ends at ID 34641 and cannot repair these newer rows.

## Backend redeployed after authorization

At approximately 20:28 Jakarta on 29 October, deployed version
`31351d58-8d35-4298-9ce4-a4e14d4f003b` to `adtools` at 100% traffic.
The bundled backend differs from the preceding production bundle only in the
timestamp parser. All 54 relevant tests passed before deployment.

The upload used `keep_assets: true`, the existing production bindings, and preserved
secrets. After deployment, bindings, compatibility date/flags, placement, logpush,
observability, and tail consumers exactly matched the pre-deployment settings.
The active production bundle exactly matches the locally verified bundle (SHA256
`f058ceac74f81ddf162de78227511fa8966be0fccf172d1d095e1ae42bc52531`).

HTTP checks with curl returned 200 for `/`, 200 for `/web-build.json` (build
`20261029070846`, version `1.3.13`), and the expected unauthenticated 401 for
`/dashboard/tabs`. Python urllib's default user agent was blocked with Cloudflare
1010, so public endpoint checks used curl. Static assets were not rebuilt/uploaded.

No analytics rows were changed during this deployment. Already shifted records
still need a separate audited repair; the deployed fix corrects future ingestion.
